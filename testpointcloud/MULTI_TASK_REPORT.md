# 五个任务的相机与操作区实验

本次新增文件全部位于 `testpointcloud`。正式任务相机、FlowDP3 适配器、项目根目录
README.md 和 introduce.md 没有修改。本文给出可审阅的实验参数，尚未切换采集或训练入口。
PickCube 的较大样本结果和真实专家动作回放详见 [README.md](README.md)。

## 相机建议

相机位置和注视点均为**世界坐标，单位米**；crop 使用机器人基座坐标，不能混用。
Panda 基座世界位置约 `(-0.615,0,0)`。分辨率统一选 256×256，最终输入维持 FPS512。

| 任务 | eye（世界坐标） | target（世界坐标） | 垂直视场角 | 实验配置名 |
| --- | --- | --- | --- | --- |
| PickCube-v1 | `(0.30,-0.30,0.35)` | `(0,0,0.12)` | 60° | `low_left256_60` |
| PushCube-v1 | `(0.30,-0.30,0.35)` | `(0.15,0,0.08)` | 75° | `wide_low_left256_75` |
| StackCube-v1 | `(0.30,0.35,0.28)` | `(0,0,0.07)` | 65° | `lower_right256_65` |
| PegInsertionSide-v1 | `(0.30,-0.35,0.55)` | `(0,0.10,0.12)` | 75° | `wide_high_left256_75` |
| DrawTriangle-v1 | `(0.25,-0.40,0.50)` | `(-0.10,-0.10,0.04)` | 60° | `left256_60`，仍有采样丢失 |

PegInsertionSide 保留原来的 `hand_camera`，只调整 `base_camera`。其点数来自两台相机的
原生拼接，不能将插杆数千个原始点都归因于新外部相机。其余四个实验机器人均只有一个
生成点云的原生相机。PushCube 的操作方块实际是蓝色；StackCube 则分别统计红、绿两块；
Peg 统计插杆和插孔盒；Draw 统计黑色目标三角形轮廓与红色画迹，没有红色操作方块。

## 固定操作区 crop

在有效点转换到基座坐标后、减去 TCP 前，使用下面的轴对齐区域。每个任务内所有相机
使用同一 crop，所以相机对照没有混入 crop 改动。区域由任务随机化范围、已有轨迹中
物体表面/位姿范围和必要余量确定；优先保留操作物体和末端，不要求覆盖完整机械臂。

| 任务 | crop_min（基座坐标） | crop_max（基座坐标） |
| --- | --- | --- |
| PickCube-v1 | `(0.44,-0.23,-0.03)` | `(0.79,0.25,0.52)` |
| PushCube-v1 | `(0.40,-0.23,-0.03)` | `(1.06,0.25,0.52)` |
| StackCube-v1 | `(0.36,-0.36,-0.03)` | `(0.87,0.36,0.52)` |
| PegInsertionSide-v1 | `(0.34,-0.40,-0.03)` | `(0.90,0.62,0.52)` |
| DrawTriangle-v1 | `(0.28,-0.35,-0.03)` | `(0.80,0.18,0.52)` |

推荐配置在完整检查样本中，可见操作物体点的 crop 保留比例均为 100%，最终地面点均为0。
另外四个任务同时检查了物体几何边界，没有物体边界被 crop 切掉。这里“100%”只指相机
实际看见的点；没有补出背面或被遮挡的表面。桌面/画布仍占很多 FPS 点，普通空间框无法
同时保留贴在平面上的目标轮廓、又删除其下面的全部平面。

三角形在推荐配置的原始观测中700帧均可见，但是最终FPS仍丢掉3帧，**此配置仍不能保证
每帧保留目标**。画迹初期本来不存在，不能把全部141个画迹零点帧都视为采集失败；
完整统计区分了原始未见、crop丢失、预采样丢失和FPS丢失，见最终analysis.json。
具体是115帧原始没有可见画迹、6帧预采样丢掉可见画迹、20帧FPS丢掉预采样中的画迹。
目标轮廓的一个最差例子为episode 1/frame 206：原始200 → crop200 → 预采样19 → FPS0，
对应`DrawTriangle-v1-comparison-worst.png`，证明剩余缺失发生在采样而非未实例化。

新相机的末端覆盖也有取舍。FPS512 腕部/夹爪最少点数为 Pick 8、Push 34、Stack 31、
Peg 11、Draw 33；腕部是机器人点的子集，不能重复计入512总数。Pick 若更重视腕部，
较高右斜视 `eye=(0.28,0.24,0.50), target=(0,0,0.17), FOV=50°` 的腕部最少31点，
方块中位数10点，可作为备选。

## 为什么选这些位置

- Pick：低左斜视改善物体原始分辨率和FPS低分位；过近45°视场在全120条轨迹中会截掉
  抬升目标，俯视则常被机器人挡住。推荐配置的原始方块476 → 预采样72 → FPS11，
  采样依然是主要限制。仅增加原相机分辨率至256或384未明显改善最终FPS覆盖。
- Push：60°低视角虽有更多方块点，但部分目标圆盘越界；注视点前移且扩大到75°后，
  方块和圆盘的几何边界都留在画面内。
- Stack：低左视角会让夹爪挡住红方块，较高视角可能挡住绿方块。最初低右视角在302帧中
  红、绿都原始可见，但FPS丢了1帧绿方块；进一步降至z=0.28且使用65°后，红块最少3点、
  绿块最少2点，两者FPS零点帧都为0。相比之前的低右视角，红块中位数从7降至6，
  换取绿块连续保留。
- Peg：原基座相机太低，插杆部分出画，插孔盒受遮挡；较高左侧75°同时覆盖两者。
  插孔盒的原始零点帧46→0，FPS零点帧57→0，但盒子获得更多采样点之后，插杆FPS中位数
  25.5→14。这是明确的取舍，不能称为两个实体的点数同时提升。新外部相机本身的插杆
  原始中位数344、插孔盒3072；两相机合计才是表中的5401和3236。
- Draw：有效的远俯视原始三角形点中位数1091，但FPS中位数仍为9，且有9个目标零点帧、
  腕部最少3点；较近俯视虽增大目标投影，却有遮挡和采样零点帧。最终选择左侧斜视，
  目标FPS零点帧较少、末端覆盖更稳。其539 → 预采样70 → FPS9仍说明普通FPS对贴近画布
  的细轮廓保留不足。384分辨率没有解决这个问题。

## 计数怎么核对

每次重置后重新读取操作物体的 `per_scene_id` 和所有机器人link的实体ID；不使用红色阈值
或“离末端近就认为是机械臂”等规则。原始点保留源像素索引，crop、预采样和FPS都传递
这些索引。最终对每个FPS点回查对应相机像素的segmentation，从而统计其真实实体归属。
图中上色只用于检查；segmentation、物体位姿和几何边界都没有参与选点。

每帧保存原生RGB/segmentation、各相机像素偏移、内外参、裁剪后基座系XYZ、源索引、
TCP、FPS512 XYZ+距离特征与实体ID。审计检查源索引唯一性、segmentation映射、坐标还原、
距离通道、crop边界和地面计数，并在每条轨迹初始帧核对现有FlowDP3点云适配函数。
Draw使用只读的TCP接口视图调用相同采样函数，没有修改PandaStick类或正式适配器。
另外四个任务的最终审计共6062份有效帧/相机记录，通过了上述检查；早期退化俯视记录
明确排除在外。Pick另有4558份有效记录、9116份FPS512/1024数组通过独立审计。

## 数据和局限

另外四个任务复用 `.runtime/crop-inspection-20261006-1` 的原生关节专家记录，各3条成功
轨迹。相机候选先对每任务同样54个保存状态重渲染，再对选定候选重渲染全部状态。
Push/Stack为seed 0、1、2，Peg为seed 2、4、6，Draw为seed 0、1、2。
Draw使用`diagnostic-base-interface.h5`；各源文件及JSON的SHA256均保存在manifest。

这些是保存状态的重渲染，用于隔离相机变化。筛选与完整检查使用相同3条轨迹，
**不是独立测试集，也不是策略成功率评估**。仅Pick另外执行了原生专家动作回放。
其他任务的机器人/control/state接口还需要单独适配才能成为正式FlowDP3训练数据。
所有实验保持有效点→基座系crop→随机4096（seed42）→普通FPS512→减TCP/追加距离的流程。

早期两组完全竖直的Draw俯视候选使用了与视线平行的默认up向量，导致look_at姿态退化、
实际相机位置不正确；最终分析明确排除这些记录。重测使用`up=(0,1,0)`，检查单位四元数
并从实际内外参还原eye。其他斜视参数也在最终审计中核对实际相机位置。

因此本路线能够恢复大部分原始目标观测、改善Stack和Peg的关键实体缺失，但不能保证
最终512点里物体占大比例。桌面/画布仍占多数点，Draw仍有3帧目标完全丢失；如果后续
要求目标每帧有几十个点，仍需进一步研究采样或去除支撑平面，不能仅依赖增大分辨率。
本次没有加入实体保底采样、复制点、合成遮挡表面，也没有训练策略。

## 结果文件和复现

- [最终统计与分阶段丢失计数](runs/multi-final-report/analysis.json)
- `runs/multi-final-report/<任务>-camera-preset.json`：世界系相机pose、sensor_configs、crop、FPS参数。
- `runs/multi-final-report/<任务>-comparison-middle.png`：相同状态的RGB/FPS对照。
- `runs/multi-final-report/<任务>-comparison-worst*.png`：最少目标点帧的对照。
- `runs/multi-*-validation*/`：完整状态重渲染的HDF5、summary和manifest。
- `multi_task_experiment.py`：运行程序；`analyse_multi_task.py`：审计、排名和出图。

从项目根目录复现，例如Push完整小批量（必须使用新的输出目录，程序拒绝覆盖）：

```bash
.venv-ppu/bin/python -B testpointcloud/multi_task_experiment.py \
  --tasks PushCube-v1 --cameras baseline wide_low_left256_75 --frames 0 \
  --output testpointcloud/runs/my-push-validation
```

正式接入时必须统一录制、训练、评估和可视化的相机及crop观测契约，并重新生成训练输入。
现有checkpoint不能假定已适配本次观测变化；本目录参数目前仅供实验审阅。
